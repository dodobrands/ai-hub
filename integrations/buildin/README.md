# Buildin Integration

Интеграция с [Buildin.ai](https://buildin.ai) — вики-платформа для документации.

## Структура

```
integrations/buildin/
├── .claude-plugin/
│   └── plugin.json           # Манифест плагина
├── scripts/
│   ├── buildin.sh            # Level 1: HTTP-клиент (curl + Bearer JWT, UI API)
│   ├── buildin-pages.sh      # Level 2: CRUD + read (markdown) + delete-block; команды комментариев передаёт в buildin-comments.sh
│   ├── buildin-comments.sh   # Level 2: комментарии — треды, ответы, резолв, откат
│   ├── buildin-lib.sh        # Общие хелперы двух скриптов выше (подключается через source)
│   ├── buildin-blocks.py     # Построитель транзакций для дерева блоков (вложенность)
│   ├── buildin-comment.py    # Построитель операций комментариев: якорь, перенарезка сегментов, треды, откат
│   ├── buildin_segments.py   # Даты и упоминания текстом — общий модуль read и comments
│   ├── md-to-blocks.py       # Конвертер Markdown → блоки (таблицы, toggle, mermaid)
│   ├── buildin-publish-md.py # Движок publish-md: батчи, ретраи, режим --replace
│   ├── buildin-verify-md.py  # Сверка опубликованной страницы с исходным markdown
│   ├── buildin-nav.sh        # Level 2: Навигация и поиск по дереву
│   ├── buildin-shadow.sh     # Level 2: Shadow-индекс (локальный кеш)
│   └── buildin-login.sh      # Проверка и сохранение JWT-токена
├── tests/                     # bats-юниты: md-to-blocks, publish-md, verify-md, append-image, comment, segments
├── shadow-index.json          # Локальный кеш структуры и саммари страниц
├── commands/
│   ├── read-page.md          # Скилл: чтение страницы (URL/UUID/поиск)
│   ├── publish-page.md       # Скилл: создание/обновление страницы
│   └── buildin-login.md      # Скилл: логин через browser MCP (Google SSO)
└── README.md
```

## Быстрый старт

> Нужен плагин `hub-meta`: скрипты берут из него загрузчик `.env` (`hub-meta/scripts/load-env.sh`). При установке плагином Claude Code ставит его сам — он объявлен в `dependencies` в `plugin.json`; в клоне и subtree он и так лежит рядом.

### 1. Логин

Используй скилл `/ai-hub:buildin-login` — он откроет Buildin через Chrome DevTools MCP, выполнит Google SSO и сохранит JWT-токен в `.env` как `BUILDIN_UI_TOKEN`.

Или вручную:
```bash
# Проверить текущий токен
./integrations/buildin/scripts/buildin-login.sh check

# Сохранить токен из буфера обмена
./integrations/buildin/scripts/buildin-login.sh clipboard
```

JWT-токен живёт ~30 дней.

### 2. Проверь подключение

```bash
./integrations/buildin/scripts/buildin.sh GET /api/users/me
```

### Как выглядят ошибки

UI API отвечает HTTP 200 почти всегда, а настоящий статус кладёт в поле `code`
тела. `buildin.sh` смотрит на оба: не-успешный `code` — это ошибка, скрипт
падает ненулевым кодом и пишет причину в stderr.

```
$ ./integrations/buildin/scripts/buildin.sh GET /api/blocks/<несуществующий_id>
Error: Buildin API code 3005: Document not found
$ echo $?
1
```

Ответы без поля `code` и не-JSON тела проходят как раньше.

У каждого запроса есть таймауты: 10 секунд на соединение и 60 на весь запрос. Без них
зависший запрос вешал бы команду, а с ней и агента. Переопределяются окружением —
`BUILDIN_CONNECT_TIMEOUT` и `BUILDIN_MAX_TIME`, целые секунды. Если запрос не уложился,
`buildin.sh` пишет об этом в stderr и называет, какую переменную увеличить.

## Использование

Все команды принимают UUID или URL buildin.ai:

```bash
# Обе формы эквивалентны:
./integrations/buildin/scripts/buildin-pages.sh read <page_id>
./integrations/buildin/scripts/buildin-pages.sh read https://buildin.ai/<space_id>/<page_id>
```

### Чтение и навигация

```bash
# Прочитать страницу как markdown (рекурсивно раскрывает columns, toggles)
./integrations/buildin/scripts/buildin-pages.sh read <id|url>

# Заголовок
./integrations/buildin/scripts/buildin-pages.sh title <id|url>

# Родительская страница
./integrations/buildin/scripts/buildin-nav.sh parent <id|url>

# Дочерние страницы (включая вложенные в columns/toggles)
./integrations/buildin/scripts/buildin-nav.sh children <id|url>

# Дерево страниц (2 уровня вглубь)
./integrations/buildin/scripts/buildin-nav.sh tree <id|url> 2

# Поиск по названию (до 4 уровней вглубь)
./integrations/buildin/scripts/buildin-nav.sh search <id|url> "query" 4
```

**Даты и упоминания.** В части инлайн-сегментов `text` — не то, что видно на странице.
У даты там заглушка «‣», у упоминания — пусто. `read` и `comments` печатают их одним
модулем `buildin_segments.py`:

- дата — `2026-10-16 14:30`, диапазон — через `→`. Формат «сегодня/вчера» из UI
  зависит от дня чтения, поэтому печатается сама дата;
- упоминание человека — `@ник`. Без ника — первые 8 символов uuid: чужие почты в
  контекст агента не попадают. Список участников команда запрашивает один раз и только
  если на странице кто-то упомянут. Если список не получен, в конце вывода стоит
  пометка: короткие id тогда означают не «нет ника», а «список недоступен»;
- упоминание страницы — `[Название](https://buildin.ai/<space_id>/<page_id>)`.
  `/api/docs` кладёт в ответ лишь родителей страницы, поэтому названия остальных
  команда спрашивает у `/api/blocks`, по одному запросу на страницу. Если страницы нет
  или к ней нет доступа, печатается ссылка без названия.

### Создание и редактирование

```bash
# Создать дочернюю страницу
./integrations/buildin/scripts/buildin-pages.sh create <parent_id|url> "Заголовок"

# Обновить заголовок
./integrations/buildin/scripts/buildin-pages.sh update <id|url> "Новый заголовок"

# Добавить текст
./integrations/buildin/scripts/buildin-pages.sh append-text <id|url> "Новый параграф"

# Опубликовать markdown-файл (по умолчанию дописывает в конец)
./integrations/buildin/scripts/buildin-pages.sh publish-md <id|url> doc.md
./integrations/buildin/scripts/buildin-pages.sh publish-md <id|url> doc.md --replace

# Добавить блоки (JSON)
./integrations/buildin/scripts/buildin-pages.sh append-blocks <id|url> '<json_blocks>'

# Вставить блоки после / перед конкретным блоком (block_id — поле uuid из get-blocks)
./integrations/buildin/scripts/buildin-pages.sh insert-blocks-after  <id|url> <block_uuid> '<json_blocks>'
./integrations/buildin/scripts/buildin-pages.sh insert-blocks-before <id|url> <block_uuid> '<json_blocks>'

# Удалить конкретный блок (не страницу!)
./integrations/buildin/scripts/buildin-pages.sh delete-block <block_uuid> [parent_id]

# Архивировать
./integrations/buildin/scripts/buildin-pages.sh archive <id|url>
```

### Комментарии

Комментарий в Buildin — это тред (`discussion`), привязанный к блоку, плюс сообщения
(`comment`) внутри треда. Тред всегда выделяет фразу внутри блока, поэтому у команды
создания есть обязательный аргумент-якорь.

```bash
DIR=integrations/buildin/scripts

# Прочитать все комментарии страницы
bash $DIR/buildin-pages.sh comments <id|url>

# Только комментарии одного блока — вторым аргументом или якорем в URL
bash $DIR/buildin-pages.sh comments <id|url> <block_uuid>
bash $DIR/buildin-pages.sh comments '<url>#<block_uuid>'

# Создать комментарий к фразе внутри блока
bash $DIR/buildin-pages.sh comment <id|url> <block_uuid> 'фраза-якорь' 'текст комментария'

# Ответить в тред, закрыть его и открыть заново — id треда из вывода comments
bash $DIR/buildin-pages.sh comment-reply <id|url> <discussion_uuid> 'текст ответа'
bash $DIR/buildin-pages.sh comment-resolve <id|url> <discussion_uuid>
bash $DIR/buildin-pages.sh comment-unresolve <id|url> <discussion_uuid>

# Позвать человека: uuid участников — из members, упоминание — опцией --mention
bash $DIR/buildin-pages.sh members <id|url>
bash $DIR/buildin-pages.sh comment-reply <id|url> <discussion_uuid> 'посмотри' --mention=<user_uuid>

# Откатить comment или comment-reply — путь из строки «rollback: <путь>» в stdout
bash $DIR/buildin-pages.sh comment-rollback <путь> [--narrow] [--dry-run]
```

`comment` принимает идентификаторы в тех же формах, что и `comments`: блок задаётся
вторым аргументом либо якорем `#<block_uuid>` в URL. `block_uuid` — поле `uuid` из
вывода `get-blocks`.

Даты и упоминания `comments` печатает так же, как `read` (см. «Чтение и навигация»):
`@ник`, ссылка `[Название](…)` на страницу и сама дата. Автор без ника — первые 8
символов uuid.

#### Ввод текста

Якорь и текст можно взять из файла (`@путь`) или из stdin (`-`) — длинный текст в
bash-строке неудобно экранировать:

```bash
bash $DIR/buildin-pages.sh comment <id|url> <block_uuid> 'фраза-якорь' @comment.md
cat comment.md | bash $DIR/buildin-pages.sh comment <id|url> <block_uuid> 'фраза-якорь' -
```

Сигил `@` экранируется удвоением: `@@j.doe глянь` даёт литеральный текст
`@j.doe глянь`. Это именно текст, а не @-упоминание человека: упоминание задаётся
опцией `--mention` (см. «@-упоминания» ниже). Значение, начинающееся с дефисов
(`--force`, `-- не согласен`), пишется после разделителя `--`; это работает и для
инлайна, и для `@файла`:

```bash
bash $DIR/buildin-pages.sh comment <id|url> <block_uuid> -- '--force' 'текст'
```

Значение, равное одному дефису, означает stdin, и своего escape у него нет: литеральный
`-` берётся из файла. Пустой файл и пустой stdin отвергаются — тред без сообщения в
живой документ не уходит.

#### Якорь обязан быть однозначным

**Якорь целиком лежит внутри одного сегмента.** Сегмент — отрезок текста с единым
форматированием, поэтому фраза, задевающая границу жирного, кода или ссылки, выделена
быть не может. Команда отвергает такой якорь с разбором сегментов, а не привязывает
тред молча не туда:

```
Error: Якорь есть в тексте блока, но разорван границей сегментов. Якорь должен
целиком лежать внутри одного сегмента.
Текст блока: «лимит 100 запросов/мин»
Сегменты:
  [0] «лимит »
  [1] «100 запросов» [code]
  [2] «/мин»
Возьмите фразу короче — целиком внутри одного форматирования.
```

**Несколько вхождений — тоже отказ.** Якорь `лимит` по тексту
`безлимитный тариф: лимит 100` подошёл бы к двум местам, и первое из них — внутри
слова `безлимитный`. Команда перечисляет вхождения с контекстом и ждёт решения:
удлинить якорь до однозначного или выбрать явно через `--occurrence=N` (нумерация —
по видимому тексту блока, слева направо).

Вхождения считаются с перекрытиями: `ана` в `банана` — это два вхождения, а не одно,
и такой якорь тоже отвергается. Шаг поиска в один символ, иначе короткий якорь из
повторов молча выделял бы самое левое место.

#### Комментировать можно только прозаические блоки

Тред вешается на абзацы, списки, todo, toggle, заголовки, цитаты и callout
(типы `1, 3, 4, 5, 6, 7, 12, 13, 38`). Остальные типы команда отвергает — это
третий гард того же класса, что два предыдущих: молча привязать тред не туда
хуже, чем не привязать вовсе. Причин отказа три, и сообщение называет свою.

**В `segments` лежит не видимый текст.** У картинки (`14`) там имя файла, у
закладки (`21`) — URL и метаданные, у формулы (`23`) — исходник. Якорь по имени
файла найдётся, команда отчитается об успехе, а подсветки на странице не будет.
Сверка после записи это тоже не ловит: сегмент реально несёт `discussions`,
поэтому «наша подсветка на месте» истинно и для картинки.

```
Error: Блок типа 14 (картинка) комментировать нельзя: в segments лежит имя файла,
а не видимый текст.
Текст сегментов: «picture.png»
Комментарий к фразе поддерживают только прозаические блоки: 1 (абзац), 3 (todo), …
Видимая подпись к картинке в segments не хранится вовсе, якорем она недостижима —
прокомментируйте соседний абзац.
```

**Текста в `segments` нет вовсе.** Разделитель (`9`) пуст, а у таблицы (`27`) и её
строк (`28`) текст ячеек лежит в `data.collectionProperties` — якорь по сегментам
там не сработает в принципе, и сообщение говорит это прямо, а не жалуется на
ненайденную фразу.

**Подсветки не будет, хотя текст видимый.** У заголовка страницы (`0`) и код-блока
(`25`) сегменты хранят ровно то, что человек видит, но выделение фразы Buildin в
них не рисует: тред прикрепится и будет виден в сайдбаре, а подсвеченной фразы на
странице не появится. Проверено живьём — в абзаце и callout якорь подчёркивается,
в заголовке и коде нет.

**Неизвестный тип отвергается тоже.** Список закрытый: открытый чёрный список
пропустил бы новый тип Buildin с метаданными в сегментах, и баг вернулся бы
незамеченным — ровно так, как этот и обнаружился.

#### Дату и инлайн-формулу — только целиком

Внутри блока команда режет только сегмент, у которого `text` — сам видимый текст:
обычный текст (тип `0`, с любым форматированием) и ссылку (`3`). Два инлайн-объекта
хранят в `text` не то, что видит человек:

- дата (`1`) — заглушку `‣`, а видимую дату Buildin рисует из `startDate`;
- инлайн-формула (`8`, кнопка `√x` на панели выделения) — исходник LaTeX.

Такой объект комментируется только целиком: якорь — весь его `text`, то есть `‣`
у даты и исходник у формулы. Подсветка на странице появится, а цитатой в треде
станет этот `text`. Разрез внутри команда отвергает. Проверено живьём: формула
`x^{2}`, разрезанная по `{2`, превратилась в три формулы, и Buildin рисует все три
ошибкой разбора. Упоминания людей (`7`) и страниц (`4`) хранят пустой `text`,
поэтому якорем недостижимы в принципе. Сегмент неизвестного типа или без `type`
команда не режет: список закрытый по той же причине, что и у типов блоков.

Видимую дату якорем не найти, поэтому разбор сегментов в сообщении об ошибке
подписывает такие объекты: `[1] «‣» [дата 2026/10/16 14:30]`.

Код (форматирование `code`) резать можно, но выглядит это иначе, чем у текста:
каждый кусок разреза рисуется отдельной плашкой. Тред висит на сегменте, поэтому
выделить часть кода по-другому нельзя.

#### Что команда гарантирует, а что нет

`--dry-run` **читает** страницу, но ничего не записывает: ни транзакции, ни файла
отката, в том числе заданного через `--rollback-out`. Токен и сеть ему нужны — без
них превью не построить, потому что якорь ищется в реальных сегментах блока.

**Запись узкая.** `update` по `path: ['data']` меняет только `segments`, тред добавляется
в блок списочной операцией `listAfter` по `path: ['discussions']`. Полная перезапись
блока стирала бы чужие ключи `data` и выбивала из списка чужие треды — проверено на
живой странице: `listAfter` аддитивен, запись полного списка нет.

**Конкурентную правку команда не предотвращает, а обнаруживает и убирает за собой.**
`segments` всё равно уходят целиком из снапшота, снятого в начале команды. Перед
отправкой блок перечитывается, и если сегменты успели измениться — запись отменяется
с просьбой повторить команду. Этого мало: несколько процессов успевают сделать оба
чтения раньше первой записи (на живой странице из трёх параллельных комментариев двое
теряли подсветку). Поэтому после записи результат сверяется по факту:

- **наша подсветка не закрепилась** — значит блок переписали поверх нас. Команда сама
  снимает свой тред узкой транзакцией (`listRemove` из списка блока, `status: -1` на
  тред и сообщение) и выходит с кодом 1, прося повторить. Сегменты она при этом не
  трогает: в блоке лежат чужие, и возврат нашего снапшота стёр бы подсветку того, кто
  выиграл гонку. Файл отката в этом случае применять **не надо** — команда печатает
  этот запрет **до** самоочистки, чтобы его не проглотил её собственный сбой;
- **нашего треда нет даже в списке блока** — транзакция не применилась. `listAfter`
  аддитивен, и конкурент наш id из списка не убирает, так что создавать было нечего:
  код 1, ничего не гасится, повтор безопасен;
- **проверочное чтение не вернуло блок** (конверт ошибки, не-JSON, чужая страница) —
  об исходе записи ничего не известно. Код 2, самоочистки нет: гасить, возможно,
  успешный тред нельзя;
- **подсветку потерял чужой тред** — громкое предупреждение с перечислением и
  подсказкой, как их посмотреть. Треды остаются в списке блока и их текст цел, но на
  странице их не видно. Вернуть подсветку автоматически команда не пытается: к какой
  фразе чужой тред был привязан, она не знает, а угадывать — это ровно то, от чего
  защищают гарды якоря.

Остаточный случай, который так не закрыть: проигравший гонку убирает за собой сам, но
если чужой тред затёрли **после** того, как его команда уже успешно завершилась, убрать
за неё некому. Такой тред попадёт в предупреждение победителя — и это единственное
место, где о нём скажут. На живой проверке из четырёх параллельных комментариев двое
проигравших вычистились сами, один остался осиротевшим и был назван в предупреждении.

Базой сравнения служит **список тредов блока** после записи за вычетом тех, что были
без подсветки ещё до запуска. Список подходит, а подсветка нашего снапшота — нет:
треды, созданные параллельно, в снапшот попасть не могли, и сверка с ним пропускала
ровно тот случай, ради которого заведена.

Правки текста, легшие между вторым чтением и записью, сверка не ловит: она смотрит на
подсветку, а не на текст. Предотвратить их потерю нельзя, а обнаружить — можно: у блока
есть поле `version`, которое растёт при каждой записи, и прирост больше, чем даёт одна
наша транзакция, означал бы чужую запись в окне. Пока не сделано.

**Откат.** Перед отправкой команда сохраняет payload отката — готовое тело запроса,
которое возвращает `segments` блока, убирает тред из списка и гасит созданные
`discussion`/`comment` (`status: -1`), чтобы после отката их не показывала и `comments`.
Файл кладётся через `mktemp` в `$TMPDIR` (имя непредсказуемо, права `0600`;
переопределяется опцией `--rollback-out=<path>`). Путь печатается в stderr ещё до
отправки, а при успехе — в stdout строкой `rollback: <путь>`.

```bash
bash $DIR/buildin-pages.sh comment-rollback <путь> [--narrow] [--dry-run]
```

`--dry-run` проходит все сверки ниже и печатает операции, которые ушли бы на откат, —
ничего не записывая и не переименовывая файл. Отказ при этом тот же, что у боевого
прогона.

`comment-rollback` применяет только файлы отката `comment` и `comment-reply`. Тонкая
обёртка не должна становиться способом отправить произвольную транзакцию, тем более из
файла, путь к которому мог прийти из чужого текста. Поэтому в транзакции допустимы лишь
операции, которые пишет сам откат:

- гашение треда и сообщения (`status: -1`). Без гасимой записи файл — не откат:
  настоящий откат всегда гасит свою;
- `listRemove` из списка тредов блока или сообщений треда — только той записи, которую
  файл гасит. Иначе файл из одних `listRemove` снимал бы чужие треды и ответы;
- метка правки блока — только тому блоку, с которого файл снимает тред, или блоку из
  сверки. `status` у блока — это архивация страницы, её подложенный файл повторить не
  должен;
- возврат `segments` — только при сверке `check`, только тому блоку, по которому
  сверка, только вместе с гашением одного своего треда и только ровно обратный разрезу
  `comment`. Команда повторяет разрез на возвращаемых сегментах и сравнивает итог со
  сверкой целиком, со всеми полями. Сверки одного текста мало: через неё прошли бы
  подменённая ссылка и снятая чужая подсветка.

Всё прочее команда отвергает. Конверт запроса собирается заново тем же хелпером, что у
остальных команд.

После отправки команда перечитывает страницу и проверяет, что откат на ней виден: тред
убран из списка блока (у отката ответа — ответ из треда), а у полного отката блок
вернулся к снапшоту. Только тогда файл переименовывается в `<путь>.applied` (в stdout —
`status: applied` и `rollback: <путь>.applied`; не удалось переименовать — прежний путь и
предупреждение в stderr), и повтор
команда отвергает: второй полный откат снова вернул бы блок к старому снапшоту и стёр
подсветку тех, кто успел прокомментировать после первого. **Коды выхода:** `0` — откат
виден на странице; `1` — отказ до записи (файла нет, он уже применён, не похож на откат
или не прошёл сверку со страницей) или транзакция не легла — файл на месте, повтор
безопасен; `2` — исход неизвестен (POST оборвался, проверочное чтение ничего не
подтвердило или сама проверка упала): файл остаётся на месте, прежде чем применять снова, стоит посмотреть блок
командой `comments`.

**Сверка со страницей.** В файле отката есть служебный ключ `check` — страница, на
которой писали. Перед любым откатом команда читает эту страницу и отказывает, если:

- записей из файла на странице нет — откат уже применён или страница не та;
- гасимые записи создали не вы — так подложенный файл погасил бы чужой тред;
- запись снимается не со своего списка: тред — только с блока из его `parentId`, ответ —
  только с треда из его `parentId`, а сообщение, которое файл не убирает из списка,
  гасится только вместе со своим тредом;
- в гасимом треде есть чужие сообщения. Откат гасит тред целиком, и ответ коллеги
  пропал бы молча. Команда предлагает вместо отката закрыть тред через
  `comment-resolve` — обсуждение тогда сохранится;
- в гасимом треде есть ваши же ответы. Их откатывают их собственные файлы (строка
  `rollback:` в выводе `comment-reply`): сначала ответы, потом тред.

Оба отказа действуют и для `--narrow`: узкий откат тоже гасит тред.

**Откат треда — в два шага.** Между сверкой и записью проходят секунды, и в это окно
коллега может ответить в тред. Условной записи у API нет: запись с устаревшей
`version` сервер принимает молча. А погашенный тред `/api/docs` уже не отдаёт, так что
после отката ответ не увидеть. Поэтому команда сначала закрывает тред (закрытый
`/api/docs` ещё отдаёт), перечитывает страницу и сверяет заново. Появился чужой ответ —
тред открывается обратно, откат отказывает с кодом `1`, ничего не потеряно. Нет — идёт
сам откат. Закрытый тред на странице не виден, поэтому новый ответ в него после первого
шага маловероятен. Откат ответа и уже закрытого треда — одна запись: закрывать нечего.
Если второй шаг не прошёл, тред остаётся закрытым: повторите откат или откройте тред
командой `comment-unresolve`.

Сегменты блока ответы не меняют, поэтому сверка сегментов ниже такого не видит —
нужна отдельная проверка по треду.

**Сверка перед полным откатом.** Полный откат возвращает блок в то состояние, в котором
`comment` его **прочитал**. Если после комментария блок кто-то правил или
комментировал, такой возврат стёр бы чужие правки и подсветку. Поэтому `comment` кладёт
в `check` ещё блок и сегменты блока после своей записи. `comment-rollback` перед полным
откатом сверяет блок с ними. Совпало — откат идёт. Не совпало, блока на странице нет или
страница не читается — полный откат отвергается с кодом `1`, и команда предлагает узкий:

```bash
bash $DIR/buildin-pages.sh comment-rollback <путь> --narrow
```

Узкий откат снимает только свой тред: убирает его из списка блока и гасит записи, а
сегменты не трогает. Если блока треда на странице уже нет, узкий откат отказывает до
записи: снимать тред не с чего. Id треда на сегменте остаётся, но Buildin такой тред не
подсвечивает — проверено живьём. Файл без `check` (записанный до появления сверки)
команда не применяет: сверить его со страницей не с чем. Вручную через `buildin.sh`
такой файл не отправляйте — так он миновал бы все проверки отката. Разметку блока можно
вернуть в интерфейсе Buildin. В `check` отката ответа только страница: сегменты он не
трогает.

Откат гасит сообщение, но не отзывает уже разосланное уведомление: если в сообщении
было `--mention`, человек его уже получил.

Права `0600` команда ставит и дефолтному файлу (`mktemp`), и файлу по
`--rollback-out` (запись под `umask 077`). У **уже существующего** файла права свои —
перезапись их не меняет. Дефолтные файлы отката не удаляются и копятся по одному на
комментарий: чистить их — ваша забота.

**Коды выхода.** `0` — комментарий создан и подсветка на месте. `1` — ничего нашего в
блоке не осталось, повтор безопасен (гонка, из которой команда вышла сама, или
неприменившаяся транзакция). `2` — **исход неизвестен**: повторять вслепую нельзя,
сначала посмотрите блок на странице. Код 2 даёт сбой самого POST, сбой проверочного
чтения, ответ без блока и неудачная самоочистка.

При успехе id треда печатается в **stdout** строкой `discussion: <uuid>` — там же,
где `create` печатает id новой страницы, — а следом строка `rollback: <путь>` с файлом
отката. Сырой ответ транзакции наружу не идёт.

Id созданного треда дублируется в stderr **до** отправки: если POST оборвётся, узнать его будет
неоткуда — `curl` в `buildin.sh` идёт без `-S` и на обрыве молчит. Слепой повтор после
такого обрыва повесил бы второй тред на ту же фразу: видимый текст блока после разреза
не меняется, и якорь находится снова.

**Проверки перенарезки.** Сверка склейки текста сегментов стоит в билдере как
регрессионный сторож: при нынешней реализации разреза она сработать не может (склейка
равна исходному тексту по построению), но ловит будущую правку `split_segments` — это
проверено тестом с намеренно сломанным разрезом. Рядом стоят проверки, которые
разойтись способны, и у каждой свой тест со своей поломкой: непустые части, допустимое
изменение числа сегментов, тред ровно на одном новом сегменте, сохранность всех полей
сегмента (`url`, `type`, `enhancer`) и неприкосновенность соседей.

Под капотом одна транзакция из шести операций: `discussion` (тред), `comment`
(сообщение), узкий `update` сегментов, `listAfter` по `discussions` и обновление
`updatedAt` страницы и блока — правкой страницу отмечает и UI (снято с живой страницы).
Без узкого `update` сегментов и `listAfter` тред создаётся, но остаётся неприкреплённым —
на странице его не видно.

#### Ответ в тред

`comment-reply` дописывает сообщение в конец существующего треда. Id треда — строка
`Тред <uuid>` в выводе `comments`. Страница обязательна: прочитать тред по id API не
умеет (`/api/discussions/<id>` отвечает 404), и команда ищет его среди тредов страницы.
Текст передаётся в тех же формах, что у `comment`: строка, `@файл`, `-` для stdin,
`@@` для литерального `@`, `--` перед значением с ведущими дефисами.

Запись — ровно то, что шлёт UI (снято с живой страницы): запись `comment` той же
формы, что первое сообщение треда, и `listAfter` по `comments` треда. Сам тред и блок
ответ не трогает. Операция над списком узкая: перезапись полного списка выбила бы
параллельный ответ.

В закрытый тред команда не пишет и отсылает к `comment-unresolve`: закрытый тред
Buildin на странице не показывает, и ответ в нём легко пропустить. Тихий успех хуже
отказа, а открыть тред можно явной командой.

Гарантии те же, что у `comment`. Id ответа печатается в stderr ещё до отправки, при
успехе — в stdout строкой `comment: <uuid>`, а следом `rollback: <путь>`. После записи команда перечитывает страницу
и проверяет, что ответ есть в треде. **Коды выхода:** `0` — ответ в треде; `1` — отказ до
записи или транзакция не применилась (ничего не создано, повтор безопасен); `2` —
исход неизвестен: вслепую не повторять, сначала посмотреть тред командой `comments`.
Перед отправкой сохраняется файл отката (`--rollback-out=<path>`, права `0600`): он
убирает ответ из треда и гасит его (`status: -1`). Применяется он той же командой
`comment-rollback`, что и откат `comment`, с той же сверкой: гасится только ваш ответ.

#### @-упоминания

`--mention=<user_uuid>` упоминает участника пространства в начале сообщения — и у
`comment`, и у `comment-reply`. Опцию можно повторять, повторы одного uuid схлопываются.

Ограничения намеренные. Упоминание встаёт только в начало: позвать человека — это всё,
что нужно агенту, а упоминание посреди текста потребовало бы своего синтаксиса и
экранирования. Упомянуть можно только человека: упоминание страницы (`type: 4`) никого
не уведомляет, а ссылку на страницу можно дать текстом.

```bash
bash $DIR/buildin-pages.sh comment-reply <id|url> <discussion_uuid> 'посмотри, пожалуйста' --mention=<user_uuid>
```

Упоминание — сегмент `type: 7` с uuid человека и пустым `text`, ровно так его пишет UI
(снято с живой страницы). Упоминания встают в начало и отделяются пробелом, как их
набирает человек: `@j.doe @a.smith посмотрите`. Отдельного сообщения на уведомление UI
при упоминании не шлёт ни по HTTP, ни по WebSocket: уходит только транзакция с таким
сегментом, а в сокет за это время — лишь плановый `PING` (перехвачено на живой
странице). Команда шлёт то же самое, поэтому уведомление, если Buildin его рассылает,
рождается на сервере так же, как из UI.

uuid участника даёт `members` — участники пространства страницы, по строке
`<uuid>  <nickname>`:

```bash
bash $DIR/buildin-pages.sh members <id|url>
```

Почты команда не печатает: для упоминания хватает uuid, а вывод уходит в контекст
агента. Каждый uuid из `--mention` команда сверяет с тем же списком: опечатка дала бы упоминание никого, и тот, кого хотели позвать,
ничего бы не узнал. Не участник пространства — отказ без записи. Список участников не
получен — тоже отказ.

#### Резолв треда

`comment-resolve` закрывает тред, `comment-unresolve` открывает его заново. Id треда и
страница — как у `comment-reply`.

Запись — ровно то, что шлёт UI (снято с живой страницы): одна узкая операция, `update`
треда с `{"resolved": true}` или `false`. Сегменты и список тредов блока резолв не
трогает. Подсветку закрытого треда Buildin просто не рисует, а после повторного открытия
она возвращается.

Если тред уже в нужном состоянии, записи нет: выход `0` с пояснением в stderr. После
записи команда перечитывает страницу и сверяет флаг. В stdout — `discussion: <uuid>` и
строка `status: changed` (записано) или `status: noop` (уже было так): код выхода у них
один, а различать их агенту нужно. **Коды выхода:** `0` — тред в нужном
состоянии; `1` — отказ до записи (треда на странице нет, он удалён, неверные аргументы)
либо транзакция не применилась; `2` — исход неизвестен (сбой POST или проверочного
чтения). Резолв идемпотентен, поэтому повтор безопасен при любом коде — в отличие от
`comment`, где слепой повтор повесил бы второй тред. Файла отката у резолва нет: его
откат — обратная команда.

### Расширенные блоки из Markdown

`md-to-blocks.py` конвертирует Markdown-файл в дерево блоков Buildin, а
`append-blocks`/`insert-blocks-after`/`insert-blocks-before` создают его целиком —
включая **вложенные** блоки (таблицы, сворачиваемые секции, многоуровневые списки),
которые плоский append выразить не может. Маппинг заголовков совпадает с выводом
`read` (round-trip): `#`→level 1, `##`→level 2, `###`→level 3.

```bash
DIR=integrations/buildin/scripts

# Обычный путь: одной командой, блоки дописываются в конец страницы
bash $DIR/buildin-pages.sh publish-md <id|url> doc.md

# Перепубликация документа целиком: содержимое страницы заменяется,
# ссылки на дочерние страницы сохраняются
bash $DIR/buildin-pages.sh publish-md <id|url> doc.md --replace

# Тот же конвертер отдельно — когда блоки нужны как JSON для точечной вставки
python3 $DIR/md-to-blocks.py doc.md > /tmp/blocks.json
bash $DIR/buildin-pages.sh insert-blocks-before <id|url> <block_uuid> "$(cat /tmp/blocks.json)"
```

```bash
# Сверить опубликованную страницу с исходником (рассчитано на --replace)
python3 $DIR/buildin-verify-md.py <id|url> doc.md
python3 $DIR/buildin-verify-md.py <id|url> doc.md --keep-h1   # если H1 публиковали
```

Сверка сравнивает страницу целиком с одним файлом, поэтому осмысленна после
`--replace`. После append лишнее на странице — норма, и такие расхождения
помечаются отдельной пометкой, а не выглядят поломкой.

`publish-md` добавляет к конвертеру то, чего нет в голом `append-blocks`: разбиение
на транзакции по 25 блоков, повтор сетевых обрывов и транзиентных ответов сервера
(429, 5xx), безопасный порядок замены — новые блоки заливаются первыми, старые
удаляются последними, поэтому сорванная публикация не оставляет страницу пустой, —
и сохранение блоков-ссылок на дочерние страницы при `--replace`. Операции собирает
всё тот же `buildin-blocks.py`.

Поддерживаемые блоки:

| Markdown | Блок Buildin | type |
|---|---|---|
| `#` … `###` | заголовок | 7 (level 1–3) |
| `<!-- collapse -->` перед заголовком | сворачиваемая секция (всё до след. заголовка того же/высшего уровня — внутрь) | 38 |
| `-` / `*` (вложенность по отступу) | маркированный список | 4 |
| `1.` `2.` | нумерованный список | 5 |
| `- [ ]` / `- [x]` | чек-лист | 3 |
| `> текст` (ведущий эмодзи → иконка) | выноска (callout) | 13 |
| `---` | разделитель | 9 |
| ` ```lang ` | блок кода | 25 |
| ` ```mermaid ` | mermaid с preview-рендером | 25 |
| `\| таблица \|` | нативная таблица | 27 + строки 28 |
| абзац | параграф | 1 |
| `**bold**` `*italic*` `` `code` `` `[t](url)` | inline-форматирование | — |

**Мягкие переносы.** Внутри пункта списка и внутри абзаца перенос строки не создаёт
новый блок: строка с отступом и без маркера считается продолжением пункта (как в
CommonMark) и клеится к его тексту через пробел — inline-разметка, разорванная
переносом, тоже собирается. А вот в выноске (`>`) **каждая строка остаётся отдельной
строкой** внутри одного callout — так задумано (шапки документов держат `> **Источник:**`
/ `> **Участники:**` разными строками), поэтому содержимое выноски верстать по ширине
не надо: перенос попадёт в опубликованную страницу как есть.

Опция `--shift-headings` сдвигает уровни заголовков на 1 (`##` → level 1), если
нужны более крупные секции. Изображения и цвета текста в Markdown-конвертере не
поддерживаются (отсутствуют в синтаксисе Markdown); картинку на страницу добавляет
отдельная команда `buildin-pages.sh append-image <page> <file> [caption]` — она
сама грузит файл в S3 Buildin (`getS3FileUploadInfo` → presigned PUT) и создаёт
image-блок (`type: 14`, `data.ossName`).

`read` понимает эти типы в обратную сторону — таблицы, `<!-- collapse -->` и
вложенность восстанавливаются при чтении страницы как Markdown.

### Shadow-индекс (локальный кеш)

Локальный кеш структуры и саммари страниц для мгновенного поиска без API-запросов. Растёт органически: каждое чтение страницы автоматически обновляет индекс.

```bash
# Мгновенный поиск по title + summary
./integrations/buildin/scripts/buildin-shadow.sh search "RFC"

# Дерево из кеша (без API)
./integrations/buildin/scripts/buildin-shadow.sh tree <page_id>

# Полный дамп для LLM-анализа (субагент может прочитать и понять структуру)
./integrations/buildin/scripts/buildin-shadow.sh dump

# Статистика и устаревшие записи
./integrations/buildin/scripts/buildin-shadow.sh stats
./integrations/buildin/scripts/buildin-shadow.sh stale 30
```

Поиск через `buildin-nav.sh search` автоматически проверяет shadow-индекс перед обращением к API.

`tree` без аргумента берёт корень снаружи, в порядке: `BUILDIN_ROOT_PAGE_ID` (из `.env` или окружения), затем `buildin.root_page_id` в `team-config.json`. Если корень нигде не задан, команда печатает подсказку и выходит с ошибкой: раньше на её месте был ID страницы конкретной команды, из-за чего у всех остальных `tree` молча печатал пустое дерево.

## Особенности Buildin API

- **Поле `parent`** — `GET /v1/pages/{id}` возвращает `parent` объект: `{"type": "page_id", "page_id": "..."}` для дочерних страниц или `{"type": "space_id", "space_id": "..."}` для корневых. API пространств (`/v1/spaces`) недоступен.
- **Два формата блоков** — новый API хранит контент в `data`, legacy — в именованных полях (`heading_1`, `paragraph`). Скрипты поддерживают оба.
- **Нет `plain_text`** — заголовки берутся из `text.content` внутри `rich_text` items.
- **Поиск — `api/search` КРАЙНИЙ способ.** Официальный API (`/v1/search`) сломан (500). UI API `/api/search` работает, но качество низкое (нерелевантные результаты) и поиск scoped на конкретный space (не по всем — легко искать не в том пространстве). **Приоритет:** shadow-индекс → обход дерева от базовых страниц (`buildin-nav.sh children <page_id>`, попутно наполняет shadow-индекс) → и только потом `api/search` с явным space_id.
- **Доступ** — UI API (JWT из Google SSO) видит все страницы пользователя. Официальный API-токен видит только расшаренные боту страницы (иначе 403).
- **SDK** — [GitHub: next-space/buildin-api-sdk](https://github.com/next-space/buildin-api-sdk) (Java + TypeScript, OpenAPI spec)

## API Reference

Интеграция использует **UI API** (не официальный API). Base URL: `https://buildin.ai`, авторизация через JWT-токен из Google SSO.

| Метод | Endpoint | Описание |
|-------|----------|----------|
| GET | /api/users/me | Текущий пользователь |
| GET | /api/pages/{id} | Получить страницу с блоками |
| POST | /api/pages/{id}/transactions | Создание/редактирование (транзакции) |
| GET | /api/blocks/{id} | Получить блок по UUID |
| POST | /api/search | Поиск по пространству |

Официальный API (`api.buildin.ai`, `/v1/...`) также существует, но имеет ограничения: поиск сломан (500), нет доступа к пространствам, видит только расшаренные боту страницы.
