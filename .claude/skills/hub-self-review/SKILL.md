# hub-self-review: один раунд ревью вместо трёх

Ревью в репозитории глубокое и проверяет фиксы по коду, а не по ответам в тредах.
Каждый раунд находит и регрессии от фиксов прошлого раунда. Дешевле найти всё самому
до первого пуша.

## Шаг 0. Механика

`bash .claude/skills/hub-preflight/scripts/preflight.sh` должен дать `FAIL 0`.

## Шаг 1. Собери контекст

```bash
git diff --stat origin/main...HEAD
git diff origin/main...HEAD -- integrations/ tests/ .claude-plugin/
```

Прочитай `REVIEW_GUIDELINES.md` и правила из скилла `hub-script-dev`.

## Шаг 2. Линзы

Пройди диф по каждой линзе. Если диф больше ~300 строк, раздай линзы параллельным
субагентам (каждому: диф, линза, требование вернуть только находки с файлом, строкой,
сценарием отказа и уверенностью), потом сведи и отбрось дубли.

1. **Тихий отказ и ложный успех.** Для каждой сетевой и файловой операции: что увидит
   агент при 401, 500, обрыве сети, пустом токене, неверном ID, ошибке в теле при HTTP 200?
   Если rc=0 или «ничего не найдено», это находка.
2. **Контракт вывода.** stdout парсится в каждой ветке? Ошибка в stderr одной строкой?
   Созданный id напечатан? Нет трейсбека?
3. **Обещания против кода.** Выпиши каждое утверждение из README, описания PR,
   комментариев (`--dry-run ничего не отправляет`, `права 0600`, `покрыто тестом`) и найди
   код или тест, который это доказывает. Не нашёл: убери утверждение или допиши код.
4. **Тесты доказывают?** Для каждого нового теста: сломай проверяемую строку, тест
   краснеет? Стаб умеет отказывать? Тест не зависит от env разработчика?
5. **Опасные пути.** Неизвестный флаг, опечатка в флаге, пустой аргумент, спецсимволы
   (`"`, `\`, переводы строки, кириллица под `LC_ALL=C`), коллизия временных файлов.
6. **Все сценарии установки.** Standalone, subtree в overlay, marketplace-кеш, skill через
   симлинк, bash и zsh. Касается любого пути к скрипту или `.env`.
7. **Агент узнает о фиче?** Новая возможность описана в `commands/*.md` или `SKILL.md`
   с примером вызова и видом отказа, а не только в README.
8. **Обезличивание.** Ни одного реального имени, хоста, ID, логина. Плейсхолдеры по
   конвенции `your-company`, `<card_id>`, `j.doe`, `MyService`.
9. **Регрессии соседей.** Кто ещё зовёт изменённую функцию? `grep -rn '<func>' integrations/`.
   Изменение общей функции задевает всех вызывающих.

## Шаг 3. Чини и перепроверяй

Каждую находку уровня «реальный сценарий отказа» чини сразу, с тестом, который на
старом коде красный. После всех фиксов повтори шаг 0 и линзы 1, 3, 4 по новым изменениям:
фиксы рождают регрессии.

## Шаг 4. Описание PR

```markdown
## Проблема
<что ломалось у пользователя или агента, с воспроизведением>

## Что изменено
<по пунктам>

## Доказательства
| Утверждение | Где доказано |
| --- | --- |
| ошибка API даёт rc=1 и сообщение в stderr | `integrations/<name>/tests/<file>.bats`: «<имя теста>» |
| ... | ... |

## Префлайт
Итог: FAIL 0, WARN N. <разбор каждого WARN>

## Вне PR
<замеченное, но не исправленное здесь>
```

## Шаг 5. Ответ на ревью

- Отвечай на тред ссылкой на коммит фикса и тест, который его закрепляет.
- Не пиши «исправлено», пока не перечитал код после фикса: следующий раунд проверит.
- Несогласие аргументируй сценарием, а не мнением. Снятое замечание переноси в «Вне PR».
