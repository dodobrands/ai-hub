# hub-pr-triage: чтобы улучшения доезжали до main

Открытые PR, которые висят неделями, это улучшения, которых у пользователей нет. Чаще
всего причина не в качестве, а в том, что PR дублируют друг друга, стоят в цепочке или
никто не назначен ревьюером.

## 1. Сбор

```bash
gh pr list --state open --limit 50 \
  --json number,title,author,headRefName,baseRefName,updatedAt,mergeable,mergeStateStatus,reviewDecision,isDraft,files \
  > "${TMPDIR:-/tmp}/hub-prs.json"
```

Для каждого PR: `gh pr view <n> --json body,reviews,comments` по необходимости (тело
часто говорит «мержить после #N» или «заменяет #M»).

## 2. Анализ

- **Пересечения по файлам**: пары PR, которые меняют одни и те же файлы. Отдельно
  отметь, если один PR удаляет файлы, которые другой правит: конфликт при любом порядке.
- **Дубли по смыслу**: похожие заголовки и ветки, одинаковая тема (версии манифестов,
  резолвер, `.env`). Какой из них свежее, полнее, с ревью.
- **Цепочки**: `baseRefName` не `main` или в теле «поверх», «после». Порядок мержа.
- **Состояние**: `CONFLICTING`, `BEHIND`, падает CI (`gh pr checks <n>`), нет ревью,
  последнее обновление больше 14 дней назад.
- **Версии**: два PR поднимают версию одного плагина: второй после мержа первого получит
  конфликт или откат версии.

## 3. Отчёт

Коротко, таблицей:

| PR | Тема | Состояние | Связи | Рекомендация |
| --- | --- | --- | --- | --- |
| #N | ... | CLEAN, нет ревью 40 дней | поверх #M | мержить после #M, нужен ревьюер |
| #K | ... | CONFLICTING | дублирует #L | закрыть в пользу #L |

Ниже: предлагаемый порядок мержа, список «закрыть как дубль» с причиной, PR без
ревьюера. Отдельно предупреди, если работа, которую пользователь собрался начать, уже
есть в открытом PR.

## 4. Действия

Сам ничего не меняешь в PR. Если пользователь попросит, по его подтверждению можно:
оставить комментарий о дубле, сделать rebase своей ветки, закрыть собственный PR.
Чужие PR закрывает или мержит только человек.
